# Deployment

PARALLAX 0.1.0 has two public surfaces that do not run an agent: a
static site and a read-only Streamlit app. This file says how to
publish or launch them. It does not record a live URL. No deploy was
performed for this document, and repository visibility was not changed.

## GitHub Pages

The workflow is [`.github/workflows/pages.yml`](../.github/workflows/pages.yml).

What it does:

- On a pull request, a validation job checks the files in `site/`.
  It does not publish.
- On a manual `workflow_dispatch`, the same validation runs. The deploy
  job runs only when that dispatch is on `main`.
- Push is not a trigger. A merge to `main` does not publish the site.
- The deploy job uploads the `site` directory and calls
  `actions/deploy-pages` with `preview: false`.

### Visibility and settings

GitHub Pages for a public project site is available on a public
repository. A private repository does not get that free project site.
This release does not change visibility. If the repository is private,
the workflow can still validate on a pull request, and the deploy job
will not produce a public site until an owner makes the repository
public and enables Pages.

Before the first deploy, in the GitHub repository settings:

1. Open Settings, then Pages.
2. Under Build and deployment, set Source to GitHub Actions.

The workflow does not flip that setting by itself. The workflow comment
names the conventional project URL that GitHub would assign after a
successful deploy. That URL is unverified. The site does not link it,
and this document does not repeat it as a working address.

### What the validator checks

The pull-request job fails unless the four canonical pages are present:
`site/index.html`, `site/research/index.html`,
`site/how-it-works/index.html`, and `site/try/index.html`. It also
requires `site/research.html`, `site/method.html`, and `site/try.html`.
Those three files are client-side redirects to the directory routes.
Each redirect keeps the query string and the hash fragment, and it uses
`location.replace` so the old address does not stay in history. The
stylesheet, the script, the brand assets, the pipeline diagram, and a
1200 by 630 PNG social preview are required too. The check rejects
root-absolute paths, a canonical link, the unverified Pages URL in the
page body, `.html` in a canonical page link, and credential markers.
The script must not call `fetch` or `XMLHttpRequest`. Navigation labels
are Home, Research, How It Works, and Try PARALLAX.

The home page references `styles.css`, `app.js`, and `assets/` from
`site/`. Nested pages use `../styles.css`, `../app.js`, and
`../assets/`. Links between pages are relative directory paths such as
`research/` and `../how-it-works/`, not root-absolute `/research/`
paths. That is required because the project site is hosted under
`/parallax-mcp/`.

### Smoke test without publishing

From the repository root, with Python 3 available:

```powershell
python -c "import pathlib; print('site files', len(list(pathlib.Path('site').rglob('*'))))"
```

The authoritative check is the workflow's validation job. Run it by
opening a pull request, or by dispatching the workflow on a branch
that is not `main` if you only want validation. Dispatching on `main`
is a publish. Do not dispatch on `main` until the owner wants the site
public.

Serving `site/` locally is a static-file check, not a GitHub deploy:

```powershell
python -m http.server 8765 --directory site
```

Open the local index and follow Home, Research, How It Works, and Try
PARALLAX. Stop the server when you are done. A local port is not the
Pages URL.

## Streamlit

The dashboard entry point is [`streamlit_app.py`](../streamlit_app.py)
at the repository root. The bundled data is
[`src/parallax/dashboard/catalog/release.json`](../src/parallax/dashboard/catalog/release.json).

### Local

```powershell
uv sync --extra dashboard
uv run --extra dashboard streamlit run streamlit_app.py
```

Python 3.12 is required. The process does not read an API key.

### Streamlit Community Cloud, if an owner chooses to use it

This release does not create a Streamlit Cloud app and does not name a
live app URL.

If an owner connects the repository later:

- Main file path: `streamlit_app.py`
- Requirements file: [`requirements.txt`](../requirements.txt), which
  is the dashboard extra exported without hashes and without the
  project itself. Streamlit Cloud installs that file and the app
  imports `parallax` from `src/` via the path insert in
  `streamlit_app.py`.
- Python version: 3.12
- No secret is required to view the bundled catalog. Do not add
  `OPENAI_API_KEY` to the app's secrets for a public viewer. The
  dashboard code does not call a model.

`requirements.txt` is generated by uv for the dashboard extra. It is
not a second lockfile for the research extras. Do not add `crewai` or
`openai` to that file so that a public app can run agents. The public
app is a viewer.

### Read-only behavior

The app loads the catalog or, when the reader selects it, a local
`runs/` directory on that machine. It can display one BYOA report file
the reader chooses. It does not import a factory, does not execute
Python from the report, and does not start an agent. There is no Run
Agent control.

Uploading a report is a display of JSON the reader already has. The
page accepts one report up to the limit implemented in the dashboard
and does not store it as a research result. Do not upload secrets.

`.streamlit/config.toml` disables Streamlit usage statistics and keeps
the toolbar minimal. That file is safe to publish. Other files under
`.streamlit/` are gitignored.

## What is not deployed

- No hosted agent runner
- No public arbitrary-Python endpoint
- No paid inference from Pages or from the dashboard
- No automatic GitHub Release
- No change to repository visibility
